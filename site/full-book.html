Welcome — Read Me First

Who this book is for

This book is for anyone who is getting code written for them — by ChatGPT, Claude, Gemini, OpenCode, a friend, or your nephew — but who cannot (and does not want to) become a programmer just to use it safely.

Maybe you asked an AI for a little script that renames your photos, tidies your bookkeeping CSV, or scrapes your own sales page. It gave you a block of code, said "just run this," and you felt that familiar flutter: I am about to run something I genuinely do not understand, written by someone/something that has never seen my computer. That flutter is correct. It is also completely normal. This book exists because that moment — running code you can read but not write — deserves a real, honest method, not a shrug.

You do not need any programming background. You do not need to memorize anything. The whole book fits around one habit we will build together: read a little, test a little, keep a way back. Everything else is detail supporting that habit, including the lessons where we fail — because running unfamiliar code will occasionally do something surprising, and a calm recovery is a much better skill than pretending it never happens.

What you will learn

By the end of this book you will be able to:

  1. Understand what code even does — plainly: programs are recipes that fetch, change, and create files, talk to the internet, and run other programs. It's all recipes.
  2. Read AI-written code the reader's way — not like a programmer, but like an informed editor: names, comments, imports, and the handful of danger words that tell you where the risky parts live.
  3. Spot the "trust me" moments — the confident phrases and confident-looking code that deserve extra checking, because the AI never actually ran anything.
  4. Ask what could break — the question playbook that turns "it works" into "here's specifically what can go wrong, and here's how you'd notice."
  5. Test before you rely on it — playground folders, dry runs, sample data, and the run-it-twice check: cheap tests that catch the mistakes that matter most.
  6. Keep originals safe — snapshots, copies-with-names, and the golden rule that your original data should always survive even a catastrophically bad code run.
  7. Check secrets and paths — the two places AI code most often does real damage: touching files it shouldn't touch anywhere, and handling credentials it should never see.
  8. Use the copy-run-rollback routine — the core loop of this entire book, so that undo is always one step away, not a hope and a prayer.
  9. Follow a real annotated walkthrough — a complete, working, deliberately-self-defending example script, explained block by block in non-coder language.
  10. Use the safety checklist and glossary — a one-page routine and a plain-English word list you can come back to forever.

The one rule of this book

If you remember nothing else, remember this:

Never let the first time you run something be the time you actually need it.

An AI can write a script in seconds, but it has never run anything in its life. It has no computer, no files, no bad luck. So it writes code optimistically — code that works in the world it imagines. You live in the world you actually have: folders with odd names, files that are half-empty, a network that drops, and Tuesday evening when you're out of patience. The routine in this book — copy, run dry, run small, run for real — exists to translate imagined success into verified success safely, every single time, in about ten minutes.

That's it. That's the whole philosophy. The rest is how.

Where I name a concrete tool or menu, treat it as "an example, check yours."

Chapter 1 — What Code Actually Does

Before you can read code safely, you need a working mental model of what code is. Not a computer science model — a kitchen model. Once you have this one analogy, 90% of what confuses beginners about "code" stops being mysterious, and the safety chapters in this book start to feel obvious rather than exotic.

The recipe analogy (and where it runs out)

Code is a recipe written for a very fast, very literal, very dumb cook.

  • A program is the whole recipe: "Make lasagna. First boil the pasta, then brown the meat…"
  • A script is a one-page recipe — renamethese-files.txt, redo-my-spreadsheet.txt. Most AI-written code you'll get is a script.
  • The computer is the cook: it follows the recipe word for word, at absurd speed.
  • The cook is dangerously literal. If the recipe says "cut the onions," the cook cuts whatever is nearest, no questions asked — while you meant "the two onions in the fridge." The recipe had no idea what you "meant."
  • The cook never tastes anything. It doesn't notice the dish is wrong; it only notices when the instructions are impossible ("take the pan out of a cupboard with no pan"). "The lasagna tastes like salt-salt salt" is a real dish the cook will proudly serve you, because nobody told it onions aren't salt.

That last point is the core insight of this entire book: a computer running code never evaluates the outcome. If the instructions are wrong in a possible way — "delete every file in C:\Users\Dylan" when you only wanted a temp folder cleaned — the cook will do exactly that, immediately, without hesitating, without asking.

And here's where the analogy runs out in an important, uncomfortable direction: recipes only touch food. Code touches files, internet connections, and other programs. The cook can open your mail, wire money, and burn down the kitchen if the recipe says so. That's why we have safety routines you'd never need for making soup.

What a program actually consists of

Any script, in any language, is made of a few kinds of parts. You can ignore the fancy names below on a first read; they're here for the glossary to point back at.

Part What it really is Kitchen phrase
Statement One instruction. Often one line. "Preheat the oven."
Variable A labeled box holding one piece of information. The note "2 cups" taped to the counter.
Function A named mini-recipe you can call by name, over and over. "The dressing recipe" — invokes it whenever.
Condition (if) "If this, do that; otherwise something else." "If the dough is wet, add flour."
Loop (for, while) "Do the following over and over — usually once per item." "Roll one ball; repeat for the whole batch."
Comment A note written for humans the computer skips entirely. A margin note in the recipe.
Import A line that borrows somebody else's pre-written mini-recipes. "Use the store's pizza dough."

Imports matter more than beginners expect. When your script says import requests, it is borrowing someone else's internet-handling code. import os grants access to your files and folders — the cook's hands. In Chapter 2 we'll build a habit of checking imports first, because they tell you which domains of power a script holds.

Also worth knowing: most scripts you get from an AI are a main flow plus a few helper functions. The main flow is what happens when you run it; the helpers are sub-recipes it uses. When you read code in Chapter 9's walkthrough, you'll see exactly this shape.

A real tiny script, dissected

Here is a genuinely small, genuinely useful script of the kind an AI would hand you. You are not asked to write one ever — only to recognize its parts. Language is Python, chosen for readability + ubiquity.

import os
import datetime

def today_prefix():
    return datetime.date.today().isoformat()

folder = "photos"
for filename in os.listdir(folder):
    if filename.startswith("IMG_"):
        new_name = today_prefix() + "_" + filename
        print("Would rename", filename, "to", new_name)

Line by line, in non-coder language:

Code What it does Sanity check a reader does
import os Grants the script file-and-folder access. "This one touches my files."
import datetime Grants access to a catalog of date helpers. "It needs to know today's date. Fine."
def today_prefix(): Defines a helper mini-recipe producing today's date as text. "Skimmed. A date, fine."
folder = "photos" Sets the working folder to photos, relative to wherever this is run. "Which photos? Note for Chapter 7."
for filename in os.listdir(folder): Loop: once for every file in the folder. "It will act on EVERY file there. All of them?"
if filename.startswith("IMG_"): Condition: only files starting with IMG_ get processed. "Good — the ones I care about."
new_name = today_prefix() + … Builds the new name: date prefix + the old name. "Old name survives. Nothing destructive."
print("Would rename", …) Prints a plan. Does not rename. "This version changes nothing. This is a DRY RUN." (Chapter 5)

Notice what you just did without being able to write a line of code: you identified what it touches (files), what it would not do (rename), and one loose end (relative folder) that Chapter 7 turns into a habit. That is reading code, reader-style: not comprehending every character, but understanding every kind of thing it could do to your world.

What happens when you run it

A useful thing to internalize: between "code exists" and "code does anything," there is a gap. Code written by an AI has proven nothing by existing. Three moments matter:

  1. It must be written (AI's moment — seconds, effortless).
  2. It must be run (your moment — here the real world enters: your folders, your network, your bad luck).
  3. It must be relied on (a later moment — when it matters, e.g., it runs overnight, unwatched, on data you didn't back up).

The AI can never perform steps 2–3. This is why the phrase "it works on my end" is literally meaningless in an AI's mouth — a chapter 3 topic — and why Chapter 5's philosophy is: the moment code meets actual reality is the only moment that counts.

The four reader questions

Every script can be interrogated with four questions. You can't answer them perfectly on first glance, but even a half-answer flags 80% of the trouble a script can cause:

Question What it uncovers Where in the code to look
1. What does it take in? Inputs: files it reads, things you type with flags/arguments, network calls it makes The start; open(, input(, sys.argv, requests.
2. What does it change? What it creates or alters: renames, writes, database edits The middle; open(…, "w"), $file >, .write(, rename, commit
3. What does it touch outside itself? The boundaries where dangerous stuff lives — deletes, sends, emails, uploads, shell-outs DANGER WORDS. Chapter 2 gives you the exact list
4. When does it stop? Whether it knows how to stop gracefully — and whether loops have safety valves "while" loops, missing if conditions, missing maximums

Chapter 2 turns these into an actual 10-minute reading method. But keep the questions around; they're the reason a non-coder can read code: you're not reading for grammar, you're reading for power and boundaries. Power = what it can do. Boundaries = what limits that power. Dangerous code is, almost always, code with lots of power and few obvious boundaries.

You don't need to read it all

The most liberating sentence in this chapter might be this: nobody fully reads code either. Professional programmers skim constantly, selectively, and strategically — reading just enough of the right parts to answer the four questions above and the specific new risk on the table. The AI-generated 200-line script someone hands you? You will read roughly 10% of it carefully: the countryside around imports, file names, loops, and any danger words. The rest — the beautiful formatting of the HTML it generates, the long lists of test data — gets skimmed.

Reading pass Time What you do
Structure pass 2 minutes Names of the file(s), function names, comments. What is this for? Does the shape match the promise?
Power pass 3 minutes Imports, for loops, and any DANGER WORDS from the table in Chapter 2
Boundary pass 5 minutes For each contact point with your world: does it ask first? check first? have limits? refuse the dangerous version?

Ten minutes, twice. That's a full non-coder review. Chapter 9 walks one script through it step by step.

When "I can't read code" stops being true

A friendly note, since this book is written for people who self-describe that way: after years of teaching beginners, the honest observation is that practically no one can't read code. Plenty of people believe they can't because they've been shown code through the wrong lens — the lens of "understand every line" (which fails, and always would) instead of "understand what it does to me and my files" (which anyone can achieve in ten minutes per script).

Reading code is closer to reading a rental agreement than reading a novel. You're not there to admire the prose. You're there to scan clause by clause, find the ones that can legally hurt you, and refuse anything that doesn't come with a way out. That skill is learnable, teachable, and — given one morning and this book — fully inside your capability.

Let's get you the exact method.

Chapter 2 — Reading Code You Cannot Write

Chapter 1 gave you the mental model: code is a recipe for a literal-minded cook, and reading means scanning for power and boundaries. This chapter gives you the actual method — a ten-minute, three-pass way to read any AI-written script without being able to write one.

Before the method, one mindset reset. People who "can't program" tend to open a code file and feel the same dread as opening a book in a language they don't speak. But code has a superpower natural language doesn't: it's readable backwards, in any order, one part at a time. You can start in the middle, find one clause you understand, and grow out from there. There's no plot to lose. Enter anywhere, exit anytime.

Pass 1: The structure pass (2 minutes)

You're not reading yet — you're mapping. Scan top to bottom and collect, on a sticky note or in a comment at the top of your notes:

Files, and what they claim to be. The file name itself is data. rename_photos.py promises one thing; backup_and_email_and_delete.py promises four things. Multi-promise scripts get extra suspicion; single-promise scripts get slightly less.

The comments at the top. AI-written scripts usually open with a header comment block explaining usage. Read it — but read it as a claim, not a description. The comment was written by the same confident author whose claims we'll audit in Chapter 3. Header comments often genuinely lie by omission: they say what a script does, not what changes it makes.

The function names. Functions are the script's table of contents. Just reading them in order usually tells you the story:

Function sequence The story it tells you before reading a single body
find_files, parse_dates, build_new_name, rename_safely, main Takes files, works out new names aligned to dates, renames with a safety emphasis. Coherent.
load_config, connect, fetch_all, transform, push_to_remote, cleanup Reads settings, goes to the network, fetches data, changes it, sends it somewhere else, then "cleans up" — and cleanup is exactly the kind of vague word that hides deletes. Be more suspicious.
obfuscate, encode_payload, do_request, decode_response A network thing that hides what it's sending. Anytime "encode/obfuscate" appears without an obvious honest purpose, stop and question.

Naming honesty is a real signal. An AI-generated script with a function called rename_safely might still not rename safely — functions can be ignorantly or aspirationally named — but it's more likely than one named do_it. More importantly, a name like push_to_remote is a boundary marker: it names a part of your world (somewhere remote) the script will touch.

Pass 2: The power pass (3 minutes)

Now read for four specific kinds of lines. You're allowed to skip everything else.

1. Imports — who is it borrowing power from?

Import you'll see What power it grants Read it as
os, shutil, pathlib, Path Files and folders — the cook's hands "This touches my files."
requests, urllib, httpx, fetch/axios (JS) The internet — sends and downloads "This talks to the outside world."
subprocess, child_process, exec, spawn Runs other programs "This can do literally anything the Other Program can do."
smtplib, email, nodemailer Sends email "This sends mail as me."
json, csv, sqlite3, database Reads/writes structured data, maybe databases "This changes data records, not just files."
schedule, time.sleep in loops, threading Runs over time / in parallel "This doesn't necessarily end when I expect."
crypt/bcrypt/hashlib with no clear reason Password or credential handling Red flag. Why does a photo-renamer need this?

2. Loops — what is it doing once for every thing?

for loops are where scripts scale up their effect. "Rename 3 files" and "rename 30,000 files" can be the same line of code. Find each loop and ask: over what collection, and is the range what I'd expect? A silent classic: a loop over os.listdir(".") — which includes files you forgot exist, plus system clutter the script will now chew on.

3. Conditions — what are its safety valves?

if statements are the script's boundaries. For each loop or destructive action, look uphill: is there a check that says "this thing exists," "this thing isn't empty," "this thing matches what I expect"? A script whose dangerous line has an if guarding it is infinitely tamer than the same dangerous line with nothing above it. Beginners should learn to spot the void: a destructive line standing naked in the code, nothing between it and execution.

4. Danger words — the specific classics.

Danger word Typical meaning Why non-programmers should know it
remove, unlink, os.remove, del Deletes a file — gone, no undo, no trash The cook doesn't use a trash can.
rmtree, shutil.rmtree, rm -rf Deletes a folder and everything inside it Nuclear. Chapter 7.
"w" mode, open(f, "w"), WriteAllText Overwrites a file with new content Old contents replaced forever.
write() on an existing file (JS/Go-style), > in shell Same as above, different costume
subprocess, os.system, backticks in shell code Runs another program with these words as arguments Bugs here can become arbitrary commands run as you.
requests.post, fetch(url, {method: "POST"}) Sends data somewhere over the network Where to? That's a question for Chapter 3/4.
curl piped into bash or sh (download-and-run in one line) Downloads a script and runs it immediately The single most "trust me" pattern in existence.
chmod, sudo, Authorization: Bearer Changes permissions / does privileged things / sends a credential Chapter 7 twice.
.env, config, password, token, api_key Credential-adjacent words anywhere Instant Chapter 7 reading pass.
git push --force, rm -rf .git Rewrites or destroys your version history Refuse automatically.

You do not need to memorize this table to use this book; you need to skim with it in mind, and let Chapter 10's checklist remind you. Pro readers google unknown words rather than skip them — and if an AI is beside you (OpenCode, ChatGPT, etc.), the fastest move is: "What does this exact line do? What's the worst realistic thing it could do?" — no shame in that, ever. The AI can't read your mind, but it can annotate its own work; using it for that is Chapter 4's job.

Pass 3: The boundary pass (5 minutes)

Now you read, slowly, only the contact points — the places where the script touches Anything That Exists:

  1. Every file it might open, write, rename, or delete. Trace each one: is the name hard-coded ("photos") — which is brittle but predictable — or assembled from something flexible? Where does the flexible part come from: your typing, a config file, an AI guess?
  2. Every network send. What data goes where, and is the destination a name you recognize and approve?
  3. Every external program it runs. A script that shells out to rclone, git, ffmpeg, or node inherits all of those programs' powers. You should know which ones and why.
  4. Endings. Does the script end when you'd expect? Or does it loop forever / run on a schedule / wait for more work? Anything that "doesn't necessarily stop" needs an extra look at Chapter 5 (the run-twice rule).

For each contact point, run a small three-question audit:

  • ☐ Does it check first? (Does the code verify the thing exists, is non-empty, matches expectations, before acting?)
  • ☐ Does it ask me first? (For anything irreversible: does the script prompt — or at minimum support a dry-run — or just act?)
  • ☐ Does it limit itself? (Loops bounded? Files restricted to one folder? Sizes capped? Retries limited?)

Three yeses = a well-bounded script. Two or fewer = you found exactly where to point your Chapter 4 questions. This is the whole reader's game: notice where the power is, then check whether anyone built fences around it.

What to do when you hit something you truly don't understand

You will, often. Three moves, in order:

  1. Note it and keep scanning. Non-programmers' biggest reading mistake is bailing out at the first hard line, as if reading requires total comprehension. It doesn't. Exit and reenter; mark it ? and move on. Many "?"s resolve themselves from context two paragraphs later.
  2. Ask your AI to explain that exact line, like this: "Explain line 14 like I've never programmed. What does it do? Worst realistic thing it could do? Is there a safer version?" Asking per line works much better than asking "explain this whole file" (the answer will be confident, generic, and too long). Line-by-line keeps the AI honest.
  3. If it still doesn't resolve: it goes on the risk list. Anything you don't understand as a reader is, by definition, a boundary whose power you haven't assessed — treat it as a candidate risk, and let Chapter 4 turn your list into pointed questions before you ever run anything.

One warning about reading AI code that reads "fine"

AI-written code is usually beautiful. Consistent spacing, nice function names, friendly comments, tidy structure. It doesn't look like a beginner's chaos; it looks like a senior engineer's prose. This is a trap worth naming in plain terms: looks-professional and works-safely are different axes. Beautiful code with no error handling will crash the same way ugly code would; a confidently commented script can still hard-code a wrong path. In Chapter 3 we'll target the claims made about beautiful code; here, just stamp this on your brain: style is not safety. You're reading for power and fences, not for elegance.

Chapter 3 — Spotting the "Trust Me" Moments

Somewhere in every AI-assisted project there comes a moment when the confident voice says something like:

"This will work — I've handled the edge cases. Just run it."

That sentence is the "trust me" moment. Not because the AI is lying — it isn't, it's usually sincere — but because it can't know. It cannot see your folders. It cannot run anything, ever, anywhere. It has no memory of last week's broken attempt. Every claim it makes about code "working" is a prediction about a world it has never touched, delivered in the confident tone of someone who has.

This chapter teaches you to hear that tone. Not to distrust AI generally — it's a phenomenal, mostly-reliable assistant — but to react to confidence the way experienced computer people do: confidence is interesting information; it is not evidence.

Why the AI sounds so sure

Generative models are trained to produce likely-sounding text. When you ask "will this work?", the statistically likely answer is an assured one, the same way autocomplete completes "Thanks so mu—" with "ch!" Look at what the AI is without anthropomorphizing it: a master of the shape confidence takes in text. It will produce shape-confidence even about things that fail immediately when run.

Three deep reasons AI claims are weaker than they sound:

Reason The plain-English version
It has never executed anything It can't get a runtime error, watch a crash, or discover a typo. It uses languages it has only ever read.
It doesn't know your machine Your folders, your filenames, your half-converted backups, your Windows quirks — absent from its world unless a previous message said so.
It predicts plausible, not true "It works!" is plausible-sounding and gets generated even if the code contains an obvious bug. Plausibility is the currency; truth must be supplied by you.

Phrase-by-phrase decoder

Treat these as five-second reactions: notice the phrase, file the message under "needs a specific check." Phrases are ordered roughly by frequency.

The AI says What it can actually mean What you respond
"Just run this." "I wrote something." "Not yet — walk me through what it touches, then I'll dry-run it."
"I've tested it / it works" "I believe it works." (It cannot have any test evidence.) "Show me exactly how to test it, step by step, and what output to expect."
"This is safe." "This is safe for a file layout I imagined." "What's the worst thing it does if a file is missing / named weird / already up to date?"
"I've handled the edge cases" "I can list plausible edge cases." "List the edge cases you handled, then the three you didn't."
"It's fine on my end" Nothing. There is no end. (Silently note it; move to Chapter 5.)
"Don't worry about that warning." "The warning is one I see often." "Explain the warning in plain words. I'll paste it if it shows for me."
"Should work now." (after a fix) "I changed something." "Great — what changed, and how do I re-test the same way?"
"You don't need to back anything up for this." A guess about your pain tolerance "I'm backing up regardless. Where should the snapshot live?"
"This minimal version is temporary, we'll harden it later" Next week never comes "Fine — but what does the temporary version refuse to touch?"
"Error X is harmless." "Error X is common." "Common when, on what setup? What should I do if mine persists?"

Notice the pattern in the responses: they all convert a feeling into a test. The decoder's whole philosophy: never accept a claim about the future when you can turn it into a check about the present.

Trust-me code patterns (the ones without words)

Some trust-me moments hide inside the code itself, no confident sentence needed. Memorizing these shapes is high-yield — they're the classic "worked perfectly in the demo, destroyed my Tuesday in practice" patterns.

Code/command shape Trust-me-ness Why it deserves a second look
Deletes before creating (rm, del, rmtree, then regenerate) High If the regenerate fails halfway, you're left with fewer files than before. Correct version: build the new thing fully first, then swap.
Downloads-and-runs in one line (curl piped into bash/sh, or .sh/.ps1 scripts fetched and executed) The max You skipped every safety layer this book has. Refuse, or download first, read briefly, run in a sandbox copy.
Overwrites existing files (open(x, "w"), > redirection, WriteAllText) without a "does it exist?" check High The old version of your file is being silently replaced forever.
git push --force / force flags anywhere Very high "Trust me" aimed not at files but at your history. Refuse unless you personally understand exactly why.
Long, clever "one-liners" accomplishing many things Medium-high Compact = hard to read = your reader's method can't see boundaries. Ask for the boring twelve-line version.
Code that pipes your project contents into the network (uploading before asking) Very high Chapter 7's domain; a trust-me moment with your secrets attached.
Anything with a comment saying # TODO: add error handling Explicit The boundary it will need (Chapter 2) is openly missing.
Scheduled/background execution (cron, while True:, "watcher", --daemon) High Runs when you're not watching. The inverse of the copy-run-rollback philosophy.
Changes many files in one pass ("batch," "bulk," "all files in") High Destructive scale. The right version has a --limit 3 for a rehearsal (Ch 5).

Two classics deserve their own paragraphs because they're so common.

The delete-then-recreate pattern. An AI writes git workflows, build scripts, and cache-cleanup scripts this way constantly: remove the old thing, then re-make it. In the AI's imagined world the second half always succeeds. On your Tuesday the second half fails — network hiccup, typo'd path, a file already open in another program — and now you have deleted your originals and have no replacements. The ask that fixes it: "Rewrite so nothing is deleted until its replacement fully exists and is verified. Then delete the old one." That request is so useful it has a folk name in our house: "no-gap version."

The perfect-world input assumption. The script reads one file. Not zero. Not two. Format exactly as imagined: field names spelled right, dates consistent, headers present. Then it meets your actual CSV where someone typed the date three different ways and one row is empty. The failure mode isn't just a crash — it's a silent drift: the script skips rows, or honestly processes 97 of 100 without telling you which. The ask that fixes it: "Before doing real work, verify the input: right file, right columns, non-empty, and report how many rows you'll process — then compare with how many you did."

The AI repeated-my-own-mistake moment

A special trust-me worth naming. When you paste your own broken attempt (or the previous AI's answer) into a chat and the new answer confidently copies its assumptions — the wrong path, the wrong column name, the invented library — the new answer inherits those bugs with total confidence. Signs: the answer starts "Great code!" or "Your approach is basically right" — then keeps your bug intact. Fixes: include the original goal, not just the broken code ("I wanted X; this claims X; here's the full error"); and when correcting a previous failure, explicitly restate what reality was ("the folder is named photos not Photos").

What a real "trust me" escape looks like

Watch the move happen — the moment where a beginner's instinct beats a confident tone. Scenario: you ask for a script that resizes images. The AI answers with beautiful code and says "This handles everything — just replace the folder path and run it."

Your instinct: "everything" — the word "everything" is doing a lot of work there.

The escape, in 45 seconds of typing:

  • ☐ "What does 'everything' include, specifically? What are three things it does not handle?"
  • ☐ "What folder does it write the new images to — same folder, new subfolder, or does it delete the originals?"
  • ☐ "Is there a mode that processes exactly three images as a rehearsal so I can eyeball them before running the rest?"
  • ☐ "If a file in the folder is corrupt or uninstall-sized, does it crash, skip, or stop the whole batch?"

That's not professional paranoia; that's four cheap questions that take less time than the confident answer took to generate. Chapter 4 turns this instinct into a full playbook. For now, keep the sentence: listen for the confident verbs; answer them with specific, small, ever-so-slightly skeptical questions.

The honest baseline: most AI code is fine

It's easy to read this chapter as paranoia. It isn't. The majority of small scripts an AI writes for simple file tasks are fine — and the trust-me habits in this book are what let you say that with your own eyes instead of a leap of faith. You're not becoming a skeptic; you're becoming a calm verifier — somebody whose confidence comes from tests run, not vibes received. That disposition will serve you far beyond this book's subject.

Chapter 4 — Asking What Could Break

Chapter 3 trained your ear for over-confidence. This chapter gives you the questions — a playbook of asks that, used before running anything, will catch most of what can go wrong. It's structured as a conversation you can have with your AI in a few minutes. The questions are also useful, with light adaptation, for a friend or nephew who wrote you a script: the goal is precise communication about risk, not interrogation.

Two framing ideas before the list.

First: breakage is a planning question, not a code question. Asking an AI mid-task "will this break?" tends to produce reassurance ("I've handled that"). Asking before it writes ("before you write it — what could this break?") produces genuinely useful analysis, because the answer shapes the plan rather than defending a finished product. Ask early. Ask as design, not audit.

Second: you are not Looking for no; you're looking for specifics. An answer like "we should handle missing files" is a specific — it names a failure and implies a guard. An answer like "it's robust" is a vibe — note it and re-ask. The quality bar for this chapter's questions is: nameable failure, nameable guard.

The opening move: the pre-mortem

Before the AI writes anything, ask the question this chapter is named for:

"Before you write it — what could this break? Walk me through the ways this could go wrong on my machine, in plain English. Then decide what to do about each."

This is called a pre-mortem: imagine the project already failed, then ask why. People love the phrase because it works: it converts vague anxiety into a list. Expect the first answer to be short (AIs front-load one or two risks). Then pull the thread with, one at a time:

  • "Which of those risks is the most expensive to fix after it happens?"
  • "What's a risk you didn't list because you assumed I'd never hit it?"
  • "For each, what would I notice on my end if it happened — a crash, a weird filename, or silent wrongness?" (Silent wrongness is the expensive category. It's what Chapter 5 is really about.)

You'll usually get a shortlist of 3–5 real risks. You are not expected to fix them. You carry them into Chapter 5 as the checklist of "things I'll watch in the test run." That's the whole loop: ask early, turn risks into things-to-notice.

The core question set

These eight questions cover most scripts, most failure modes, and take maybe three minutes of typing. They're ordered not by importance but by conversation flow — like a small interview.

# Ask this What you're really asking
1 "What files and folders will this read, and what will it change? List them, including any subfolders." Scope. If the list surprises you, the plan is wrong before code exists.
2 "Can it run in a mode that changes nothing — a dry run or plan-only mode?" The rehearsal option. If "no," ask for it now (Ch 5's cornerstone).
3 "If I run it twice in a row, does it do something wrong the second time — copy twice, duplicate, corrupt?" Whether it's repeatable. Accidental double-runs are the most common how-did-this-break story in real life.
4 "What happens if the network is down halfway through?" Whether the failure is graceful (stop, tell you, leave things as they were) or messy (half-changed everything).
5 "What happens if an input file is empty, missing, or misnamed?" The perfect-world-assumption check from Chapter 3.
6 "How do I undo this? Exactly what does rollback look like?" The escape hatch. If the honest answer is "you can't," the design changes before code is written.
7 "Does it need any secrets — keys, tokens, passwords — and if so, where do I put them?" Chapter 7's territory, asked up front instead of discovered in the code.
8 "What's the simplest version that still does the job — no extra features?" Scope discipline. Every extra feature is extra read-time, extra test-time, extra risk.

Question 6 deserves a moment of resonance: undo as a design requirement, not an afterthought. A script whose rollback story is "restore from your backup" is fine if you have a backup — that's Chapter 6's job. But many scripts can have better undo for free: writing outputs to a new folder instead of in place, a --dry-run default, a rename batch written to a log first. Asking "how do I undo it" first is the single highest-value question in this list, because it moves undo from hope into design.

Question drills for specific moments

Beyond the core set, here are pointed asks for situations you'll recognize.

When the AI proposes something you didn't ask for:

"I asked for X. What did you add beyond X, and why? Can I have the version with only X?"

Almost every AI answer includes unsolicited cleverness — retries, parallelism, caching, logging frameworks. Some are genuinely helpful; some are read-time you don't want. Choose consciously.

When you're about to run something for the first time on real data:

"You've never seen my actual folder. What are the three things most likely to be different from what you assumed? What should I check before running?"

This question produces gold surprisingly often — the AI knows exactly what it assumed, and listing its assumptions briefly forces those assumptions into the open where you can compare them to reality.

When something works and you're about to rely on it:

"Before I rely on this weekly, stress it: what input, timing, or environment would break it? Is there a small test I can run each time to confirm it's healthy?"

This is how Chapter 5's "health checks" are born — the five-second test you rerun forever after.

When a fix fails twice:

"We've tried twice and it keeps failing. Stop patching. Re-look at the problem: what's the likely real cause, and what's the simplest script that avoids it entirely?"

Two failed patches usually mean the design is fighting reality, not the code. Ask for a rethink, not fix number three.

When code does something you can't explain (the Chapter 2 "?"):

"Line 14 — explain like I've never programmed, in one paragraph: what does it do, why is it here, what's the worst realistic thing it could do, and is there a safer version?"

Getting the AI to write the checklist for you

A trick worth its own section because it doubles your leverage. After the AI finishes a task, instead of you inventing tests, ask:

"Write me a short testing checklist for what you just built: what a healthy run looks like, three edge cases to try on purpose, and one 'rollback drill' to prove I can undo it. Keep it to one page, plain English."

You get four things free: the healthy-run definition — protecting against the silent-nothing failure — deliberate edge cases instead of accidental ones, an undo practice, and a re-readable document for next time (file it next to your script; Chapter 6's snapshot habit pairs beautifully with it).

Use the same trick on the risks side, at the very start:

"Before writing code: list the top 3 ways this could break, each with the plain-English symptom I'd notice, and one guard you'll build in."

That's the pre-mortem with built-in alarms. Keep both lists; they'll be your Chapter 5 test plan almost word for word.

When it's not an AI — applying the playbook to people

Half of this playbook transfers, word for word, to asking a human friend or colleague about their code. What changes is tone: with a person, soften ("walk me through" → "can you remind me," "what could this break" → "what are you worried about?"). The conversational moves — ask early, ask for specifics, ask about undo, ask for the simplest version — work identically on people; often better. A good rule from years of tutoring humans: a beginner's sincere question is never a burden. If someone acts like it is, find a different mentor.

A worked mini-conversation

From a real session, compressed. You asked for a script that backs up your writing folder to a backups subfolder, once a day, keeping the last 7 copies.

  • ☐ Pre-mortem first: "Before you write it — what could this break, in plain English, and what will you do about each?" → The AI lists: wrong folder path; disk filling up; backup deleting existing backups incorrectly; silently backing up zero files. Guards: verify source exists, check free space, name backups with today's date, log the count of files backed up. → Notice item three: "deleting existing backups." A backup routine that touches old backups is exactly the delete-before-create trap from Chapter 3. Your questions found it before a single line was written.
  • ☐ "Run-twice check?" → Confirms two same-day runs are safe (same filename, overwrite same-day copy only).
  • ☐ "Undo?" → "Delete today's backup file; originals are never touched." Good boundary story.
  • ☐ "Secrets?" → None needed. (Checked anyway, Chapter 7 habits.)
  • ☐ "Simplest version?" → Drops parallel copying, adds logging; file copied count remains.
  • ☐ Testing plan requested → "Back up a scratch folder of 5 fake files; then back up again same day and confirm one file, not two; then disconnect the source folder and confirm it refuses loudly rather than backing up nothing."

Ten minutes, and every risk in the room has been named, guarded, and has an alarm you'll actually see. That's the difference between hoping code works and being the person in charge of it.

The one-sentence version

If you take one reflex away: before code exists, ask what could break and how you'd notice; after code exists, ask what to rehearse and how to undo. Everything else in this book is the discipline of doing that on purpose.

Chapter 5 — Testing Before You Rely on It

You've read the code (Chapter 2), heard the trust-me claims (Chapter 3), and gotten the risk list (Chapter 4). Now comes the step that actually earns your confidence: running the thing — carefully. This chapter is the linker between "code that exists" and "code I can rely on," and it's built around one sentence: test in a classroom, not the kitchen. You never want a first-ever run aimed at files you care about. Practice on the copies and the fakes; build confidence cheaply; then aim it at the real thing.

The playground habit

Create a playground folder — a scratch copies-area for rehearsal runs — outside your real data. Name it something unmistakable, like 00-playground. Inside it, build small fakes that imitate your real situation badly on purpose:

Fake to include Why
A copy of 3—5 real files (copies — copies, as Chapter 6 will hammer) The closest thing to the real test, run on real data without risk.
One empty file Catches the perfect-world assumption (Ch 3).
One file with a long or odd name (IMG_2026-??-01 (final) (final)v2.jpg — spaces, parentheses, symbols) Filenames break more scripts than any other cause.
One file whose type the script surely didn't expect (a .txt in your photo folder) Finds out whether it skips gracefully or crashes.
One duplicate (same content, two names, or the same name twice in different subfolders) Catches overwrite and dedupe bugs.

Five minutes of setup, used forever. Every script you ever get from an AI gets its first run here, before it ever meets /photos. Bonus: a playground is exactly where the walkthrough in Chapter 9 does its first run.

The dry run

A dry run is a run that performs no changes: it shows what would happen. Every script in this book's universe should have one. Use the pre-mortem question from Chapter 4 ("can it run in a mode that changes nothing?") and be persistent: dry runs are easy for the AI to add and hideously valuable to have.

To retrieve facts from an unknown script: check for --help (Unix-y scripts often expose a help screen), or just skim the code for words like dry, plan, --apply, or a comment that says "default is dry-run." If a script has no dry run and you want one, the make it default trick works wonders: ask for "the safest mode to be the default, with a flag like --apply to allow real changes." Never add the reverse. Defaults are habits, and habits should be safe.

What a good dry run shows:

  • The list of changes it would make (before → after)
  • A count ("42 files") — so you can compare with your expectation ("should be 43 — why one less?")
  • Any skips ("2 files left untouched because…")

Reading a dry run is a skill of its own, and it's Chapter 2's four questions again, but with reality supplying the answers this time: what will it take in, what will it change (now visible!), what does it touch, when does it stop. You should be able to answer "does this dry run look like what I asked for?" in one yes/no sentence. If the answer is close-but-not-quite, stop running things — that discrepancy you noticed is exactly what Chapter 4's risk list was asking you to find.

Sample runs, small to large

When something has a dry run, add rehearsal sizes: deliberately run it on a tiny subset of real data before letting it loose on the whole. Ways to do it, cheapest first:

  • ☐ Make a mini real folder: copy 3 real files into 00-playground/mini-real/, run there.
  • ☐ Use a limit flag if the script has one (--limit 3, --max 5) — a good AI adds these if asked.
  • ☐ Run on the playground's deliberately weird fakes first: empty file, longer names, duplicates.

Reading order matters: fakes catch crashes and logical errors; mini-real catches assumption errors (filenames you didn't think about, content quirks). Run both. It's the difference between "the recipe has no impossible steps" and "the recipe is wrong for my kitchen's ingredients."

What to actually watch

Non-programmers watching their first run tend to look at the end ("did it finish?") instead of the middle. Train yourself on these four:

Watch Healthy looks like Unhealthy looks like
Number processed Matches the count you had 97 of 100, unexplained; or 1,037 when you have 42
First few changes You can name each one as right "Wait, why is that file in the list?"
End state Files you didn't expect to touch are… untouched Mtime of your original files changed; things lower in the folder tree moved
Skips and warnings Skips have reasons printed Empty, or "Warning (suppressed) x214"

The silent-nothing failure is the sneakiest: the script finishes instantly, prints nothing, and claims success. It did nothing wrong (nothing at all) — wrong folder, wrong extension match, permissions blocked. The ask that catches it early: "End with 'Done: N things changed.'" A healthy run ends with a number. Then check that number against your own count. (Also note the mirror-image failure: the loud crash that feels worse than the silent nothing but is better for you. A script that stops immediately with an error, having changed nothing yet, is behaving exactly right — that's what Chapter 4's "does it fail gracefully?" answer looks like in the wild.)

The run-twice rule

If a script is one-run-and-done, add a second run to the audition before you adopt it. Then check whether it:

  • Says "nothing to do" (idempotent and correct — the best case)
  • Does the same thing again safely overwriting its own earlier output (fine for some tasks)
  • Duplicates, corrupts, deletes, or mixes up files (broken — report back to the AI with the run-twice observation)

Why? Because in real life you will run things twice: out of habit, after an interruption, because "did I even click run?" haunted you. The run-twice check catches the whole accident class for the cost of one extra click on safe data. For the walkthrough in Chapter 9, it's built in; the example script is dry-run-first and refuses to overwrite existing (so it says "already done — nothing to do", which you would read as healthy).

Health checks after adoption

Once a script becomes part of your routine — the "this runs every week" script — give it a health check: a tiny, repeatable test that takes 60 seconds and tells you it's still itself:

  • ☐ Same count? (42 files in; 42 files counted.)
  • ☐ Makes the expected kind of change on the playground copy first?
  • ☐ Same rollback path proven? (Extra-good check when the script version changed since last run.)

Recording it in one line each time (2026-10-27 — run on mini-real: 5 files, correct; dry again: "nothing to do" — healthy) builds a personal log that's both evidence and history; you'll appreciate it the day an update turns the script wrong. Set it up with Chapter 4's closing-habits ask ("write me a short testing checklist").

When to escalate the testing level

Some scripts deserve more than playground+fakes. Escalate when any of these are true:

Trigger Escalate to
It touches files outside its own folder (anything in Documents, System, your backups) Snapshot your originals first — Chapter 6 — before even the dry run
It talks to the network at all Check where exactly (Ch 4 Q5, Ch 7); consider airplane-mode testing for network-optional paths
It deletes anything, anywhere no-gap version + rehearsal on 3 files only; count checks after
Other people depend on the output (family calendar, business books) Add a buddy check: someone else skims the output before you rely on it
It runs unattended (on a schedule, a watcher, a server) Run it scheduled-but-in-the-playground first — never first-run unattended on real data

The one-piece-at-a-time principle

If a script does several things at once and one of them is the risky part — say it "renames files and emails you a summary" — it's fine to ask the AI to split it: "Give me version one: renames only. Version two: adds the email step." Each piece gets its own audition; the risky piece never hides inside a bigger working thing. Programmers call this modularization; you can call it "one thing at a time, please" and you get the same benefit.

Where this chapter ends and Chapter 6 begins

Everything here assumed you're playing with copies and fakes. The moment a script is aimed at files your heart cares about — your photos, your writing, your books — you need to know that even a bad run leaves the originals alive. That's Chapter 6: keeping originals safe. It's the chapter that makes everything in 1–5 stress-free, because once originals are guaranteed, mistakes become lessons and nothing is precious. On we go.

Chapter 6 — Keeping Originals Safe

Everything in Chapters 1–5 only works if one thing is guaranteed underneath: when a run goes wrong, the originals survive. This chapter is about making that guarantee boring, cheap, and repeatable. It's written for people whose data includes irreplaceables — years of photos, a manuscript only they wrote, their business's records — and who have deleted something once in their life and never want to feel that again.

The golden rule

The originals always have a copy that no run, no script, no AI, and no cleaning rampage can touch — at least until the thing you're doing has been trusted.

Notice what this rule does not say. It does not say "back up everything constantly in six places" (burnout) or "never touch your files again" (not possible). It says: for the specific, narrow window in which you are giving an AI-written script its audition, your originals belong to a different universe of files — one the script could not reach if it took a wrong turn. The window closes when the script is trusted (Chapters 5's criteria) and you resume normal life.

The two-snapshot move

For any project that involves running unfamiliar code near things you care about, spend five minutes on two snapshots:

  1. The folder snapshot. A copy of the folder(s) the script might touch, zipped or plain-copied, with the date in the name: bash cp -r myproject myproject-BEFORE-autorename-2026-10-27 Vanilla-copy first; fancy tools optional. And do it before running anything, always.
  2. The everything-might-really-matter snapshot. For anything you'd be devastated to lose — books, photos, business records — one copy on a different device or drive (a second disk, a USB stick, a family computer). Two devices, not two folders. That's the "3-2-1-lite": 1 = working copy, 2 = a copy somewhere else, and ideally, 3 = history (more versions than just latest).

And for anything you'd be professionally devastated to lose, go further. But no amount of online-only redundancy makes up for skipping the local rehearsal run — Chapter 5's playground — because backup protects against loss, and a rehearsed dry run protects against breakage, which is what an AI-written script most likely does.

Three rules for naming snapshots, because respect for future-you is the actual mechanism:

Rule Reason
Date-first, purpose-second (2026-10-27-BEFORE-autorename) Sorts historically, tells you what it's protecting against.
Say BEFORE- not backup- "Backup" is vague; BEFORE literally states what it lets you return to.
Never snapshot into the same folder being processed A cp inside the same tree gets swept up by the very deleting/cleaning script you fear. Snapshot to outside the tree.

That third rule avoids a real scenario worth naming: the snapshot that eats itself. Copy /photos to /photos/BACKUP-FROM-2026-10-27 and then run a folder-wide rename, and the rename will also rename the snapshot's files, or worse, the cleaner will treat the extras as clutter. Outside-the-tree copies only.

Versioning as superpower (a friendly intro)

Snapshots are the beginner's superpower; version control is the superpower's superpower — one tool, git, that snapshots everything, constantly, automatically, with an undo. If this sounds like it's for programmers: yes, but it's also for you, and it pairs with this book's mission better than almost anything else in computing. Two options worth knowing about:

  • Word-level history (Word, Google Docs, Notion, etc. all keep edit history). If your project lives in documents, you already have a partial safety net. Use it — it's free.
  • Git (the real thing). If you'll keep working with AI on projects of files, spend one evening learning git init, git add -A, git commit -m "before trying the AI script", git restore . from the Free AI Coding with OpenCode handbook, Chapter 6. That sequence is "save a restoration point; return to it," and it works at every level: project code, prompts, drafts.

To net it out at beginner scale: a fresh snapshot before every first run; a git restore-point if the project is code-heavy. You don't need to be a Version Control Person to be safe; you need to be a Person Who Takes Two Snapshots. And since the philosophy of this book is cheap habits over perfect systems, one habit — "snapshot before first run" — is honestly enough to cover 90% of the ways an AI script can go wrong.

What "keeping originals" means for inputs vs. code

Keep these two kinds of precious separate — they don't survive the same way:

Kind Examples What to protect Why different
Your data (inputs) photos, manuscripts, spreadsheets, photos again, photos Snapshots + out-of-tree copy; playground rehearsals; dry runs Irreplaceable; and the first thing scripts run over
The script (code) safe_rename.py, the AI's many versions Version history + the chat log itself Re-generatable. Worst case you re-ask the AI.

A consequence worth making explicit: when a run looks wrong, the script is the expendable thing. Delete it without ceremony — you can re-ask. The data is the thing you saved snapshots for. Beginners sometimes protect code feelings — "I spent 20 prompts getting this perfect" — and forget the data. Scripts are disposable; data is forever. (The flip side is a warm note: keeping the prompt that worked is far more valuable than keeping the script — the prompt is short, readable by humans, and can re-create the script on any AI. Worth telling yourself that when you archive code you might discard.)

The verified-restore habit

A snapshot is only a safety net if you know how to fall into it. Once — once is enough, ever — do a restore rehearsal:

  • ☐ Snapshot a folder.
  • ☐ Delete (or modify) some files in the working copy on purpose.
  • ☐ Restore the contents from the snapshot — cp -r snapshot-things/. working-folder/ — or open the zip and copy back.
  • ☐ Confirm everything came back, then close the laptop, satisfied.

Ten minutes. The day you actually need it, it goes well, because you've done it when nothing was at stake. This is the same trick fire drills use, adapted for files. (If your backups live on another device or drive, restore from that during the drill, so you've proven the whole path, not just the copy-getting step.)

Anti-patterns: how beginners accidentally skip protection

Anti-pattern What happens Fix
Working directly on originals "because it's just a rename" Renames can collide, truncate, or mis-target; rename is still changing them Playground first; originals only after auditions pass
Snapshot inside the folder being processed Snapshot gets mutated by the script Snapshot outside the tree
"It'll be fine, it's a dry run" …for the run you did. But the third argument you passed changed the run's mode Snapshot before every first run of a new version
Snapshot stack-of-doom (14 BEFORE- copies, all outdated) None current; restoration becomes archaeology Keep the two most relevant; archive the rest into one dated zip
Only backup = same drive, different folder Drive dies, both die Second device or drive for anything devastating-to-lose
The AI offers to "clean up" your working folder as part of a bigger task Unrelated files get deleted — the silent wrongness pattern The phrase that always works: "Do not delete anything. Leave every file you didn't create. I will clean up."

That last one deserves underlining. It is possibly the single most useful sentence in this book to say to an AI when you mean it:

"Do not delete anything. Do not move anything you didn't create. Tell me what you would delete, and I'll decide."

Two chapters remain on the safety core: where scripts usually go wrong specifically (Ch 7: secrets and paths), and the routine that ties it all together in ten minutes (Ch 8: copy-run-rollback). The finish line is close, and you're doing fine.

Chapter 7 — Secrets and Paths to Check

Two things cause the real damage when AI-written code goes wrong: secrets (credentials that shouldn't be seen, shared, or uploaded) and paths (places in your file system the script shouldn't go). Neither one is exotic. Both show up in tiny beginner scripts. Both are checkable in a couple of minutes once you know what to look for. This chapter gives you the two scans that, between them, cover the worst practical outcomes of running code you didn't write.

Part one: secrets

What counts as a secret

Broader than most people think. A secret is anything another party could use to be you or to unlock something of yours:

Category Examples
API keys & tokens sk-… (OpenAI-style), ghp_… (GitHub personal access token), AWS access keys, Stripe keys, Notion/Airtable/Zapier tokens
Login credentials Passwords, sign-in cookies, saved-session files
Identity documents you'd never share Tax forms, account statements, patient records (and nurses: anything PHI), contracts
Access to your money or your store PayPal API strings, eBay/Etsy tokens, bank feeds
Private personal data Contacts, addresses, birthdates — yours, family's, clients'

An AI cannot be given a secret safely either. Any key, password, or sensitive personal file you paste into a chat is now outside your control — even with a trustworthy vendor, it lands in logs you don't read. Rule for this book: never paste a secret into an AI conversation. Not even to ask "is this key safe?" Describe it instead: "the AI asked for an API key; what should I do?"

Where AI code leaks secrets — the four classic doors

Door 1: The code hard-codes it. You asked for "use my OpenAI key" and the AI, knowing no better (you didn't provide one), wrote a placeholder like API_KEY = "sk-REPLACE-ME" — and then you filled in the real key, and now it lives in a file that Git or an upload might someday carry away. This is the most common real-world secret mishap in beginner projects. The fix is structural and easy to ask for: "Load the key from an environment variable or a .env file that's listed in .gitignore; never write it inside the code." (Your AI knows exactly what that means — it's the industry-standard shape — and the Free AI Coding with OpenCode handbook covers the .gitignore side in detail.)

Door 2: The code reads the wrong file. A script meant to process your photos also walks the folder and reads passwords.txt — not maliciously, just indiscriminately. Prevention: keep secrets outside folders scripts operate on. Physical separation is the only 100% defense; a script scanning /home/you can find things, while one restricted to /home/you/photos-editing mostly can't.

Door 3: The code sends your files somewhere. Networking plus careless file-reading: an upload accompanying a "helpful" debug log. Ask Chapter 4's question 7 up front; read network-sending code per the Chapter 2 method. If a script uploads anything, you should be able to name the destination and why.

Door 4: The AI repeats it back. If a key is already in your chat history from an earlier paste, later messages can quote it, log it, or embed it in "just a debugging print" — and screenshots of those chats end up in tutorials. If a secret ever entered a chat, treat it as leaked: rotate it now. Revoking and re-issuing an API key takes two minutes in the vendor's dashboard and is nearly always free. It's the cheapest insurance in computing and beginners skip it constantly.

The 2-minute secret sweep

Before relying on any AI-written script, run this sweep on it. If your text editor has find, you can do it in 60 seconds:

  • ☐ Search the code for the shape of keys you actually use (see table above). Expect none in code.
  • ☐ Search for the words key, token, password, secret, Authorization, where they're used.
  • ☐ Check what it reads/writes: is any file on that list instead of your data?
  • ☐ Find where secrets, if any, are expected to live — env var, .env, config file — and confirm that file is not somewhere Git would grab it.
  • ☐ If the script talks to the internet: confirm nothing sensitive travels. When in doubt, Chapter 5's airplane-mode-ish testing works here too (run offline and watch what it complains about).

If anything on this list surprises you: stop, ask your AI about it in the plain-words way (no pasting), and rotate anything already exposed. That's the whole sweep — a couple of searches, half a minute each, and the class of "oops, my key" is effectively covered.

Part two: paths

The one idea to internalize

A path is where something lives on your computer, written down. C:\Users\Dylan\Documents\book\chapter-3.docx is one; book/chapter-3.docx is another. The difference between those two is the entire concept of this half of the chapter:

Kind Written like What it says Risk level
Absolute C:\Users\…, /Users/you/…, /home/you/… A place in absolute terms — which computer, which account, everything pinned Safe but rigid: breaks on other machines unless adjusted
Relative photos, ./output, ../data A place relative to where you happen to run it Flexible but surprising: run it from the wrong folder and "photos" means a different photos

Relative is why the Chapter 1 example script had a loose end: folder = "photos" doesn't say which photos — it means "a folder named photos near wherever I happen to be run." Run it from your home directory and you probably have no such folder — or worse, you do. This is the #1 lurking surprise for beginners running scripts prepared by someone else: the script's "photos" and your photos are different folders unless proven otherwise.

The dangerous-paths scan

AI misadventures in file paths follow patterns. Scan for these:

  • ☐ Root paths. Any path that is just /, C:\, C:\Windows, ~ (your whole home!), or a drive letter with nothing after it. A script told to delete everything in such a path will happily do so. If a bare root shows up as a default, stop and ask.
  • ☐ Walking up. .. (or ../..) means "one level up." A cleanup script that computes "everything one level up from here…" is sweeping beyond its lane. Ask: how far up do you go, and why?
  • ☐ Home-wide or disk-wide operations. Anything that searches from your home folder, mentions "all drives", /mnt, backup locations ("backup!") or system directories is beyond reasonable for a fresh script. The right place is a subfolder of your project.
  • ☐ Hard-coded personal paths from the AI's imagination. C:\Users\YourName\..., /Users/username/... — never real. Replace with your actual path; verify by printing it before acting on it.
  • ☐ Wildcards in commands. rm -rf *, del *.*, find … -delete — delete-everything-matching commands. If you see one and you did not explicitly discuss it, do not run it. Ask what it would actually match — the truth may be "everything in this folder, including what you meant to keep."
  • ☐ The silent overwrite target. Where does output go? Same folder (overwrites) or a new folder (almost always what you want for iterables)? This is Chapter 3's no-gap principle again, expressed as a path question.

Rehearsing paths safely

Paths are easy to test before landing on real files, and the tests are pleasant to watch:

  • ☐ Run the script's first stage (or dry run) and note the paths it claims. In our Chapter 9 example, the dry run prints each path before touching anything.
  • ☐ Use pwd (Linux/macOS) or cd (bare, Windows) — prints the folder you're standing in relative to the script.
  • ☐ Rename one file's path deliberately (a playground file): does the script skip it loudly?
  • ☐ Feed it a path that doesn't exist: does it refuse or guess? (Guessing paths = asking for weird outcomes.)

None of these take more than a minute each. They teach you what beforehand: what the script thinks "here" is, whether it checks those beliefs, and how it fails when wrong. That's path-safety, whole.

The combined pre-launch check: one paragraph you'll memorize

Long after this book's details fade, keep the paragraph. Here it is, one breath long:

What does it read, what does it change, where does it go outside its folder, and what does it ask for secrets-wise — and where do those live?

Read (Chapter 2) and distrust (Chapter 3), and you'll have narrowed in on those four questions already. This chapter just gives them teeth: two minutes scanning for secrets, three minutes for paths, and the scary categories are covered.

Chapter 8 — The Copy-Run-Rollback Routine

Everything so far — reading, distrusting, questioning, testing, snapshots, secret-and-path scans — now folds into one repeatable loop you'll run on every piece of AI code you take seriously. It's called copy-run-rollback, and once it's a habit it will take you about ten minutes, start to finish (fifteen the first few times — that's honest and normal). It's the routine this whole book exists to teach, and by far the most important muscle here.

The name

Three moves:

  • COPY — make the situation copy-safe before anything runs.
  • RUN — execute, starting from the least destructive mode, escalating only as evidence accumulates.
  • ROLLBACK — proven, one-step undo, rehearsed before you need it.

That's the loop. When something new and untrusted enters your world (an AI script, a new version of a trusted script, first run against a new set of files), you run the loop. When you've nothing new, the loop is short — a quick dry run in the playground a second time, then carry on. The loop is what lets you use AI code as material rather than mystery, which is the actual goal of this book.

Phase 1: COPY (2 minutes)

Do these in order. They're cheap, and each one removes a whole class of bad outcomes:

  • ☐ Snapshot the folder(s) the script might touch — outside the tree, date-first names (Chapter 6). Two minutes; this is the whole safety net.
  • ☐ Check the secrets sweep (Chapter 7's checklist) — no keys in code, no secrets in the blast radius.
  • ☐ Check the paths sweep — no bare roots, no .. inheritance, no delete-wildcards you didn't discuss.
  • ☐ Read the script's structure lightly (Chapter 2's three passes — you'll be fast at this now).
  • ☐ Skim the risk list from Chapter 4's pre-mortem, and refresh memory: what am I watching for?

One crucial nuance for Phase 1: the source of truth here is the latest code. If the AI wrote version 3 while you were sleeping — this happens more than beginners expect, silently editing files — glance at what changed (git diff, or a fresh eyeball pass) before skipping anything. The trust-me moment restarts with each new version. There's no "it worked last time" for code you didn't write.

Phase 2: RUN (5 minutes, staged)

Step 1: Dry run first. playground folder (real copies), --dry-run or plan mode on, and watch the output (Chapter 5's four things to watch: counts, first few changes, untouched things, skips).

Step 2: Rehearsal run on a small slice of real data. --limit-3, or a mini-real playground folder. This is the step that catches "wrong assumptions about my files," and it's worth five minutes.

Step 3: Run-twice check on the rehearsal set. Idempotence — Chapter 5's rule — means the second run says "nothing to do." The second run's honesty is one of the best single signals you'll ever get about a script's character.

Step 4: The real run. Against actual files — this should feel anticlimactic: dry run, rehearsal, and run-twice already happened. That's success; not the drama of a first attempt, but the boredom of a prepared one.

Each step escalates only if the previous one was boring. A surprise anywhere — a count off by one, a file in the plan you didn't expect — stops the routine and sends you back to Chapters 3–4: name the surprise in plain words, ask the AI about it, re-rehearse. Surprises are cheap when caught at a dry run; and exactly as expensive as the stage where you didn't listen.

Phase 3: ROLLBACK (2 minutes — or nothing, if you already did it)

The rollback isn't an emergency measure; it's a first-class phase of the routine with two requirements:

  1. It exists. You can name the exact way you'd undo: restore snapshot; git restore .; delete the outputs folder and re-copy originals; re-run a reverse script if one exists (a "no-gap" design, Chapter 3).
  2. You've used it once, on purpose. During Phase 2's rehearsal, sometimes do the undo drill: after rehearsing real-but-throwaway changes, roll back, verify everything's identical, and then re-run. Every 10th run, drill again; and once a month at minimum. It costs two minutes and guarantees your undo knowledge doesn't rust.

Rollback drills also build a different, quieter thing: calm. Non-coders' panic around code comes almost entirely from feeling trapped — "I broke something and I don't know how to unbreak it." The drill teaches your body the way a fire drill does: this is not a cliff, this is a stairway; you have walked it.

The checklist, printable

Here's the whole routine as a one-page checklist. Print it, tape it, use it forever — or fold it in half and keep it next to your keyboard.

COPY (2 min)

  • ☐ Snapshot the folders the script will touch — outside the tree, YYYY-MM-DD-BEFORE-thing
  • ☐ Secrets sweep clean (no keys in code; nothing sensitive in its blast radius)
  • ☐ Paths sweep clean (no bare / or C:\; no unexpected ..; no delete-wildcards)
  • ☐ Three light reading passes done; risk list refreshed

RUN (5 min, staged)

  • ☐ Dry run on playground copies — watch counts, first few changes, untouched things, skips
  • ☐ Mini-real rehearsal (3–5 real files) — does the output look right, name by name?
  • ☐ Run twice — second run is either "nothing to do" or demonstrably safe
  • ☐ Now, and only now: real run. Watch the same four things. Expect a quiet run.

ROLLBACK (2 min)

  • ☐ Can I name the undo path right now, from memory? (If no: make one before continuing.)
  • ☐ Drill it on the rehearsal set, roughly every 10th run: roll back, verify identical, re-run.
  • ☐ If surprised at any stage: stop, describe the surprise in plain words to the AI, re-run from Phase 1.

Laminate it if you must (figuratively); it's the whole book in fifteen lines.

Ten-minute budget, realistically

Let's time it honestly — the routine has to fit in an evening to survive:

Stage Time
Reading passes (Ch 2) 5—8 min (fast after a few scripts; beginners take 15)
Pre-mortem questions (Ch 4) 3–5 min
COPY phase 2–3 min
RUN phases (dry, mini-real, run-twice, real) 5–8 min
ROLLBACK noted/drilled 0–2 min
Total ~15 minutes first times; ~10 once it's a habit

Fifteen minutes is the honest first-time number; don't let anyone tell you less. The habit is real once it's under ten and doesn't feel like effort. It does get there — the walkthrough in Chapter 9 comes in at roughly nine.

When the routine encounters the AI's own workflow

If you're using an agent like OpenCode directly in your project (the Free AI Coding with OpenCode route), the routine adapts cleanly:

  • Phase 1's snapshot becomes git commit before the task (plus the branch habit that book teaches).
  • Phase 2's dry run is often OpenCode's plan mode — a plan you read before it writes anything, which is a dry run for plans.
  • Phase 3's rollback is git restore and/or /undo.

The sequence stays identical, though: see it before it happens, rehearse before it's real, undo is a proven step and not a wish. That's the deeply transferable idea: the routine is tool-agnostic — it's a philosophy of staged evidence, and it works in every environment you'll ever meet, including ones that don't exist yet.

What "trusted" means at the end

The routine exits when a script has passed enough auditions that you use it without the ceremony. What enough means is your call, and here are honest criteria:

  • ☐ Three real runs, no surprises, counts verified each time
  • ☐ The run-twice check is trusted (second run always says "nothing to do")
  • ☐ The rollback has been drilled recently enough that you could do it half-asleep
  • ☐ Its failure modes are known to you — you've seen it fail (on purpose: fed it an empty file, a missing folder) and it failed gracefully

Green on all four = everyday tool; checklists optional but recommended weekly. Two greens = audition tool; full routine every time. Anything less — including code you can't read at all (Chapter 2's "?" list unresolved) — stays a full-routine tool, permanent. There's no shame in a script living at full routine forever: plenty of real code works this way, in every serious shop, all the time.

Boring, repeatable, calm. That's the whole routine. Now let's watch it happen, block by block, on a real script.

The mission

A common real-life ask. You have a folder of camera exports named like IMG_4021.jpg, and you want them renamed to 2026-10-27_IMG_4021.jpg (date-prefixed). You don't trust your memory of which is which, and there are lots of them. You asked your AI helper for a small script, and it produced this.

This walkthrough will follow the full loop from Chapter 8: read it (Ch 2 method), interrogate it (Ch 3–4), copy (Ch 6), run it staged (Ch 5), watch the secrets/paths scans (Ch 7), and rehearse rollback. Along the way we'll spot three deliberate trust-me traps — the version you got from the AI, like the first drafts of all AI code, was slightly too optimistic, and we pushed back before touching anything real. Pass 1: reading the script (structure)

Here is the script, verbatim, with the code in the left column and the reader's commentary alongside. Blocks are the named chunks of the file. Compare each row to what a less careful version would look like — that contrast is where the teaching lives.

#!/usr/bin/env python3
"""Rename photo files by prefixing the current date, e.g.:
    IMG_4021.jpg  ->  2026-10-27_IMG_4021.jpg

By default this makes NO changes: it prints a plan only.
Add --apply to actually rename. It never overwrites and
never touches paths outside the folder you give it.
"""

Block A — the header docstring. Claims, in writing: renames; by default changes nothing; never overwrites; never roams outside the folder you name. Four explicit claims is good sign (most scripts make zero). But claims are claims — Chapter 3 says we verify. Keep score as you read: by the end we'll confirm each of the four.

import argparse
import datetime
import pathlib
import sys

Block B — imports. Notice what is not here: no os-level delete helpers imported directly, no subprocess (can't run other programs), no requests (can't phone home), no shutil at top level (which would hint at move/delete powers). The script borrows only argument-parsing, dates, path objects, and system-exit. Power inventory, via imports, in ten seconds: file renames only. That's a script with a small blast radius.

def main() -> int:
    parser = argparse.ArgumentParser(description=__doc__)
    parser.add_argument("folder", help="folder containing files to rename")
    parser.add_argument("--apply", action="store_true",
                        help="actually rename (default: plan only)")
    args = parser.parse_args()

    root = pathlib.Path(args.folder).expanduser().resolve()

Block C — the command line. Two arguments and both speak English when you ask for --help. --apply defaults to false — meaning the safe mode is the default mode, exactly the Chapter 5 habit we want. Then resolve() — this turns the folder argument into an absolute path now, and prints stability: whatever wayward tricks the script does later, every path it computes is anchored to the folder you named, not to "wherever I happened to be run from." (The Chapter 7 relative-path trap, defused at the door.)

    if not root.is_dir():
        print(f"ERROR: '{args.folder}' is not a folder.", file=sys.stderr)
        return 2
    if not any(root.iterdir()):
        print(f"ERROR: '{root}' is empty — is the path right?", file=sys.stderr)
        return 2

Block D — the boundary checks. This is the block a trust-me draft omits entirely, and where our walkthrough's first trap is going to live. Two if statements, each pairing a check with a polite refusal and exit code: wrong folder → say so and stop; empty folder → probably a typo — ask the human, rather than proceed. Notice how the error messages help: they name what was wrong and suggest what might be right. Boundary, alarm, story. Three of the Chapter 2 audit's three yeses.

    today = datetime.date.today().isoformat()
    renames = []
    for entry in sorted(root.iterdir()):
        if not entry.is_file():
            continue
        if not entry.name.startswith("IMG_"):
            continue
        new_name = f"{today}_{entry.name}"
        renames.append((entry, entry.with_name(new_name)))

Block E — the planner. Nothing here renames anything. The loop only lists: walks the folder, filters to IMG_* files, builds the proposed new names, appends them to a list called renames. Two filters, both suggesting good boundaries: is_file() skips folders (no folder-rename weirdness); startswith("IMG_") targets only the files you meant. And sorted(...) — an organized pass, not a chaotic one — is a small but real clue that the author thought about reproducibility: two runs produce the same plan in the same order.

    if not renames:
        print("Nothing to do: no 'IMG_*' files found.")
        return 0
    print(f"Plan: rename {len(renames)} file(s) in {root}\n")

Block F — the count. The silent-nothing failure from Chapter 5, pre-empted. If the filter matched zero files — as it will if your files are actually called DSC_3021.jpg instead of IMG_ — the script says so out loud, with the reason, and exits successfully rather than pretending to have done work. And every run states its count up front: "rename 42 file(s)." Compare that to Chapter 5's "42 expected" — now it's a number you can check against reality.

    for entry, target in renames:
        if target.exists():
            print(f"SKIP (already renamed, stopping): {entry.name}")
            return 0
        print(f"  {entry.name}  ->  {target.name}")

Block G — plan printing with a collision guard. Before it names each proposed change, it checks: does the target already exist? If anything would be overwritten — including "it's already been renamed" — the whole plan stops right there rather than barreling through with collisions. That's the Chapter 3 no-gap principle, again in miniature. Then each line of the plan, old name → new name, printed plainly. This is the exact output Chapter 5 taught you to read: name by name, nodding or frowning at each.

    if not args.apply:
        print(f"\nPlan only ({len(renames)} file(s)). "
              "Re-run with --apply to make the changes.")
        return 0

Block H — the dry-run gate. The gate that keeps promises: without --apply, the script stops here, having changed nothing, and says how to proceed when you want the real thing. Four claims from Block A checkable so far: default mode changes nothing — confirmed; never overwrites — confirmed (Block G); state-covered count and plan — confirmed (E, G, H).

    moved = 0
    for entry, target in renames:
        try:
            entry.rename(target)
            moved += 1
        except OSError as exc:
            print(f"ERROR: could not rename {entry.name}: {exc}",
                  file=sys.stderr)
            return 3
    print(f"Done: {moved} file(s) renamed in {root}")
    return 0

Block I — the safe apply. Now — and only now — does anything change. And look how: one file per loop trip, each rename individually guarded, and any failure stops everything with a specific message about which file and why. (Not "some error occurred"; the exact one.) The final line echoes the Chapter 5 ask: "Done: N things changed." with N you can compare to the plan. If reality and plan ever disagree, this is the line that will tell you. (A two-line tail not shown here — if __name__ == "__main__": calling main() — merely hands control to the code above; nothing to audit there.)

What our three traps looked like

The chapter promised three deliberate trust-me traps found during the walkthrough. Here they are, from the first draft the AI gave us, each one caught with a question before any code ran:

Trap First draft had The question that caught it What it became
1. Optimistic world folder = "photos" — silently relative to wherever the script happened to run "Which photos, exactly — what if I run this from a different folder?" Absolute resolve() anchored to a folder you name (Block C)
2. Silent blast radius No count, no plan, no filters. Renamed every file in the folder to date-prefixed, including the script copies and your notes file "What files will this touch — list them before changing anything?" is_file() + IMG_ filter, plan printing, and a count (E–G)
3. Deleting before creating Collisions solved with os.remove(target) before renaming "What happens to a name that already exists? Delete it?!" Refuse loudly on any collision (Block G) — no deletion anywhere

Notice each one is Chapter 3/4's decoder, aimed at a specific claim. You don't need to read code better to catch these; you need to ask about the boundary of the cook's behavior. And that's the chapter's quiet lesson: three questions caught three traps. Not code knowledge — asking.

Thirty days of practice (a tiny curriculum)

If you want to own this skill, here's an honest, low-effort month of practice — one small script per week, real ones you might actually want:

  • ☐ Week 1: a single-file task (like the renamer, or a "list my files by size" script). Walk the full routine twice. The goal: the sequence feels mechanical, not scary.
  • ☐ Week 2: a script that creates files (organizer, report generator). Add output-to-a-new-folder to your default asks. Rollback drill included.
  • ☐ Week 3: a script that reads something with columns (CSV of your books, your mileage). Meet silent wrongness deliberately: give it a bad column name on purpose, watch it either catch or miss, then fix it with a Chapter 4 question.
  • ☐ Week 4: a script that touches the network (a "check my public IP" or "fetch page title" tool, on data that's yours). Secrets and paths get full checks; offline testing included.

By week's end, the loop is yours. You'll have handled every category this book covers — renames, creation, structured data, network — and the routine will have shown you both its boring successes and its genuinely useful saves.

The last word

Non-coders in the AI age have a real, unfair problem: everyone can get code now, and almost nobody was taught to use it safely. This book's answer fits in one breath — read for power, ask for specifics, copy first, run small, watch counts, know your way back — and stretches over the rest of your life as a habit.
